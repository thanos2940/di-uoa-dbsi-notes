## 📚 Εισαγωγή: Γιατί Χρειαζόμαστε Έλεγχο Συνδρομικότητας

Όταν πολλές δοσοληψίες (transactions) εκτελούνται **ταυτόχρονα**, μπορεί να δημιουργηθούν προβλήματα:

```
Παράδειγμα: Μεταφορά χρημάτων
T1: Α → Β (100€)
T2: Β → Γ (50€)

ΧΩΡΙΣ έλεγχο:
T1: Read(A) = 500
T2: Read(B) = 200
T1: Write(A = 400)  [500-100]
T1: Read(B) = 200   [Διαβάζει παλιά τιμή!]
T2: Write(B = 150)  [200-50]
T1: Write(B = 300)  [200+100]
T2: Commit
T1: Commit

Αποτέλεσμα: Τα 50€ της T2 ΧΑΘΗΚΑΝ! (Lost Update)
```

**Στόχος:** Να εγγυηθούμε ότι η **ταυτόχρονη** εκτέλεση δίνει το **ίδιο** αποτέλεσμα με κάποια **σειριακή** (serial) εκτέλεση.

## 1. Χρονοπρογράμματα (Schedules)

### 1.1 Βασικοί Ορισμοί

**Χρονοπρόγραμμα (Schedule):**
Η **χρονική σειρά** εκτέλεσης λειτουργιών από πολλές δοσοληψίες.

**Συμβολισμός:**

- $R_i[X]$: Η δοσοληψία $T_i$ διαβάζει το X
- $W_i[X]$: Η δοσοληψία $T_i$ γράφει το X
- $C_i$: Η $T_i$ κάνει Commit
- $A_i$: Η $T_i$ κάνει Abort

**Παράδειγμα Schedule:**

```
S = R₁[X] W₁[X] R₂[X] W₂[X] C₁ C₂
```

### 1.2 Τύποι Schedules

#### Σειριακό (Serial) Schedule

Κάθε δοσοληψία **ολοκληρώνεται πλήρως** πριν αρχίσει η επόμενη.

**Παράδειγμα:**

```
S₁ = R₁[X] W₁[X] C₁ R₂[X] W₂[X] C₂  [T1 πρώτα, μετά T2]
S₂ = R₂[X] W₂[X] C₂ R₁[X] W₁[X] C₁  [T2 πρώτα, μετά T1]
```

**Ιδιότητα:** Τα σειριακά schedules είναι **ΠΑΝΤΑ ΣΩΣΤΑ** (εγγυημένα consistent).

**Πρόβλημα:** Μηδενική  παραλληλία → **πολύ αργά**!

#### Σύγχρονο (Concurrent/Interleaved) Schedule

Οι λειτουργίες των δοσοληψίων **πλέκονται** (interleave).

**Παράδειγμα:**

```
S₃ = R₁[X] R₂[X] W₁[X] W₂[X] C₁ C₂
```

**Στόχος:** Να βρούμε ποια concurrent schedules είναι "ισοδύναμα" με σειριακά.

## 2. Συγκρούσεις (Conflicts)

### 2.1 Πότε Δύο Λειτουργίες Συγκρούονται

Δύο λειτουργίες $O_i$ (από $T_i$) και $O_j$ (από $T_j$) **συγκρούονται** αν:

1. Ανήκουν σε **διαφορετικές** δοσοληψίες ($i \ne j$)
2. Προσπελαύνουν το **ίδιο** αντικείμενο ($X$)
3. **Τουλάχιστον μία** είναι **WRITE**

### 2.2 Τύποι Συγκρούσεων

| Τύπος | Λειτουργίες | Πρόβλημα | Όνομα |
|-------|-------------|----------|-------|
| **WR** | $W_i[X] \ldots R_j[X]$ | Dirty Read | Ανάγνωση μη επικυρωμένης τιμής |
| **RW** | $R_i[X] \ldots W_j[X]$ | Unrepeatable Read | Η τιμή άλλαξε ενδιάμεσα |
| **WW** | $W_i[X] \ldots W_j[X]$ | Lost Update | Η εγγραφή του i χάθηκε |

#### ✏️ Παράδειγμα Κάθε Τύπου

**Dirty Read (WR):**

```
T1: W[X=100]
T2:            R[X]  ← Διαβάζει 100
T1:            Abort ← X επιστρέφει στην παλιά τιμή!
T2:                  C[X] ← Commit με λάθος τιμή

Πρόβλημα: Η T2 διάβασε "βρώμικη" (uncommitted) τιμή.
```

**Unrepeatable Read (RW):**

```
T1: R[X=50]
T2:         W[X=100] C
T1:         R[X=100]  ← Διαφορετική τιμή!
T1:                 C

Πρόβλημα: Το X άλλαξε ενώ η T1 εκτελούνταν.
```

**Lost Update (WW):**

```
T1: R[X=50]
T2:         R[X=50]
T1: W[X=40]
T2:         W[X=45]
T1: C
T2:         C

Αποτέλεσμα: X=45 (η εγγραφή του T1 χάθηκε)
```

### 2.3 Μη-Συγκρουόμενες Λειτουργίες

**RR (Read-Read):** ΔΕΝ συγκρούονται!

```
R₁[X] R₂[X]  ← Μπορούν να ανταλλαγούν
R₂[X] R₁[X]  ← Ίδιο αποτέλεσμα
```

## 3. Σειριοποιησιμότητα (Serializability)

### 3.1 Ορισμός

Ένα schedule $S$ είναι **σειριοποιήσιμο (serializable)** αν είναι **ισοδύναμο** με κάποιο σειριακό schedule.

**"Ισοδύναμο" σημαίνει:**

- Περιέχει τις ίδιες δοσοληψίες
- Το τελικό αποτέλεσμα (final state) είναι το ίδιο

### 3.2 Conflict Serializability (Κυρίαρχη Έννοια)

**Ορισμός:**
Δύο schedules είναι **conflict-equivalent** αν:

- Περιέχουν τις ίδιες λειτουργίες
- Κάθε ζεύγος **συγκρουόμενων** λειτουργιών εμφανίζεται στην **ίδια σειρά**

**Schedule S είναι Conflict Serializable αν:**
Υπάρχει serial schedule που είναι conflict-equivalent με το S.

#### ✏️ Παράδειγμα: Έλεγχος Conflict Serializability

**Schedule:**

```
S = R₁[X] W₁[X] R₂[X] W₂[X] C₁ C₂
```

**Συγκρούσεις:**

1. $W_1[X]$ vs $R_2[X]$ → WR → Σειρά: $T_1 \to T_2$
2. $W_1[X]$ vs $W_2[X]$ → WW → Σειρά: $T_1 \to T_2$

**Συμπέρασμα:** Η σειρά πρέπει να είναι $T_1 \to T_2$.

**Serial schedule:** $T_1, T_2$

```
S_serial = R₁[X] W₁[X] C₁ R₂[X] W₂[X] C₂
```

Το S είναι **conflict-equivalent** με το $S_{serial}$ → **Σειριοποιήσιμο** ✓

## 4. Γράφος Σειριοποίησης (Precedence Graph)

### 4.1 Κατασκευή Γράφου

**Αλγόριθμος:**

1. Δημιούργησε έναν **κόμβο** για κάθε δοσοληψία
2. Για κάθε σύγκρουση $O_i[X]$ πριν από $O_j[X]$:
   - Πρόσθεσε ακμή $T_i \to T_j$
   - (Ετικέτα: WR, RW, ή WW)
3. Έλεγξε για **κύκλους**

### 4.2 Θεώρημα

> **Ένα schedule S είναι conflict serializable**
> **⟺**
> **Ο γράφος σειριοποίησης είναι ΑΚΥΚΛΙΚΟΣ**

**Αν ακυκλικός:**

- Η τοπολογική ταξινόμηση δίνει την ισοδύναμη σειρά

**Αν κυκλικός:**

- **ΔΕΝ** είναι conflict serializable

#### ✏️ Solved Example: Γράφος Σειριοποίησης

**Schedule:**

```
S = R₁[X] W₂[X] W₁[X] W₃[Y] R₂[Y] W₃[Z]
```

**Βήμα 1: Βρες συγκρούσεις**

```
R₁[X] vs W₂[X]  → RW → T₁ → T₂
R₁[X] vs W₁[X]  → Ίδια δοσοληψία (όχι σύγκρουση)
W₂[X] vs W₁[X]  → WW → T₂ → T₁  ← Αντίστροφη!
W₃[Y] vs R₂[Y]  → WR → T₃ → T₂
```

**Βήμα 2: Σχεδίασε τον γράφο**

```
    ┌──→ T₂ ←──┐
    │           │
   T₁          T₃
    ↑
    └───────────┘
    
Κύκλος: T₁ → T₂ → T₁
```

**Βήμα 3: Έλεγχος κύκλου**

- Υπάρχει κύκλος → **ΜΗ Σειριοποιήσιμο** ✗

## 5. Two-Phase Locking (2PL)

### 5.1 Βασική Ιδέα

Αντί να ελέγχουμε schedules **εκ των υστέρων** (precedence graph), χρησιμοποιούμε **κλειδώματα (locks)** για να **εγγυηθούμε** serializability εκ των προτέρων.

### 5.2 Τύποι Locks

#### Shared Lock (S-lock)

- Για **ανάγνωση**
- **Πολλές** δοσοληψίες μπορούν να έχουν S-lock ταυτόχρονα
- Συμβολισμός: $LS_i[X]$ (lock shared), $US_i[X]$ (unlock)

#### Exclusive Lock (X-lock)

- Για **εγγραφή**
- **Μόνο ΜΙΑ** δοσοληψία μπορεί να έχει X-lock
- Συμβολισμός: $LX_i[X]$ (lock exclusive), $UX_i[X]$ (unlock)

### 5.3 Πίνακας Συμβατότητας

|  | **S** | **X** |
|---|---|---|
| **S** | ✅ OK | ❌ Wait |
| **X** | ❌ Wait | ❌ Wait |

**Διάβασμα του πίνακα:**

- Αν έχω S-lock και ζητάω S-lock → OK
- Αν έχω S-lock και ζητάω X-lock → Wait
- Αν έχω X-lock → Wait για οτιδήποτε

### 5.4 Πρωτόκολλο 2PL

**Κανόνας:**
> Κάθε δοσοληψία έχει **ΔΥΟ ΦΑΣΕΙΣ**:

#### Φάση 1: Growing (Ανάπτυξη)

- Μπορεί να **ζητήσει** νέα locks (S ή X)
- **ΔΕΝ ΜΠΟΡΕΙ** να απελευθερώσει κανένα lock

#### Φάση 2: Shrinking (Συρρίκνωση)

- Μπορεί να **απελευθερώσει** locks
- **ΔΕΝ ΜΠΟΡΕΙ** να ζητήσει νέα locks

**Σημείο διάκρισης:** Όταν απελευθερώνεται το **πρώτο** lock.

#### ✏️ Παράδειγμα 2PL

**Σωστό 2PL:**

```
T₁: LX[X]  LX[Y]  R[X]  W[Y]  UX[X]  UX[Y]  C
    ↑────Growing────↑   ↑──Shrinking──↑
```

**Λάθος (παραβιάζει 2PL):**

```
T₁: LX[X]  UX[X]  LX[Y]  W[Y]  UX[Y]  C
            ↑ Release      ↑ Νέο lock μετά! ✗
```

### 5.5 Θεώρημα 2PL

> **Αν ΟΛΕ δοσοληψίες ακολουθούν 2PL,**
> **τότε το schedule είναι CONFLICT SERIALIZABLE.**

**Πολύ σημαντικό:** Το 2PL **εγγυάται** serializability!

### 5.6 Παραλλαγές 2PL

#### Strict 2PL

**Κανόνας:** Κράτα όλα τα **X-locks** μέχρι **commit/abort**.

**Πλεονέκτημα:**

- Αποτρέπει **Cascading Aborts** (αλυσιδωτές ακυρώσεις)
- Αν T1 κάνει abort, δεν χρειάζεται να ακυρώσουμε και T2, T3, ...

**Χρήση:** Πιο συχνή στην πράξη από το βασικό 2PL.

#### Rigorous 2PL

**Κανόνας:** Κράτα **ΟΛΑ** τα locks (S και X) μέχρι commit/abort.

**Πλεονέκτημα:**

- Ακόμα πιο απλό
- Η σειρά commit = serialization order

## 6. Deadlocks (Αδιέξοδα)

### 6.1 Τι είναι Deadlock

**Κυκλική αναμονή:** Κάθε δοσοληψία περιμένει lock που κρατάει άλλη δοσοληψία.

**Παράδειγμα:**

```
T₁: LX[X] ✓
T₂:       LX[Y] ✓
T₁: LX[Y] ⏳ (περιμένει το T₂)
T₂: LX[X] ⏳ (περιμένει το T₁)

→ ΑΔΙΕΞΟΔΟ! Και οι δύο περιμένουν για πάντα.
```

### 6.2 Wait-For Graph

**Κατασκευή:**

1. Κόμβος για κάθε δοσοληψία
2. Ακμή $T_i \to T_j$ αν η $T_i$ **περιμένει** lock που κρατάει η $T_j$

**Deadlock Detection:**
> **Κύκλος στον Wait-For Graph = Deadlock**

#### ✏️ Παράδειγμα Wait-For Graph

```
T₁ κρατάει X, περιμένει Y (από T₂)
T₂ κρατάει Y, περιμένει X (από T₁)

Wait-For Graph:
T₁ → T₂
T₂ → T₁

Κύκλος → Deadlock ✓
```

### 6.3 Αντιμετώπιση Deadlocks

#### Πρόληψη (Prevention)

**Wait-Die:**

- Αν $T_{old}$ ζητάει lock από $T_{young}$ → περιμένει (wait)
- Αν $T_{young}$ ζητάει από $T_{old}$ → abort (die)

**Wound-Wait:**

- Αν $T_{old}$ ζητάει από $T_{young}$ → ο young κάνει abort (wound)
- Αν $T_{young}$ ζητάει από $T_{old}$ → περιμένει (wait)

#### Ανίχνευση (Detection)

- Περιοδικά ελέγχουμε τον Wait-For Graph για κύκλους
- Αν βρούμε deadlock → κάνει abort μία δοσοληψία (victim selection)

#### Timeout

- Αν μία δοσοληψία περιμένει > X δευτερόλεπτα → abort
- Απλό αλλά όχι ακριβές (false positives)

### 6.4 ΠΡΟΣΟΧΗ: 2PL ΔΕΝ Αποτρέπει Deadlocks

> ⚠️ **ΕΞΕΤΑΣΤΙΚΟ:**
> "Το 2PL εγγυάται ότι δεν θα έχουμε deadlocks" → **ΛΑΘΟΣ!**
>
> Το 2PL εγγυάται **serializability**, όχι **deadlock-freedom**.

## 7. Στρατηγική Εξετάσεων

### 7.1 Τύποι Ερωτήσεων

#### Ερώτηση Τύπου Α: Έλεγχος Σειριοποιησιμότητας
>
> "Είναι το παρακάτω schedule serializable; Αν ναι, δώστε ισοδύναμη σειριακή σειρά."
>
> ```
> S = R₁[X] W₂[Y] W₁[Z] R₂[X] W₃[X] C₁ C₂ C₃
> ```

**Μέθοδος:**

1. Βρες συγκρούσεις
2. Σχεδίασε precedence graph
3. Έλεγξε για κύκλο
4. Αν ακυκλικός → topological sort

#### Ερώτηση Τύπου Β: Σωστό/Λάθος
>
> "Αν ο precedence graph έχει κύκλο, τότε υπάρχει deadlock."

**Απάντηση:** **ΛΑΘΟΣ!**

- Precedence graph → serializability (λογική ασυνέπεια)
- Wait-For Graph → deadlock (φυσικό κόλλημα)
- Είναι **ανεξάρτητα**!

#### Ερώτηση Τύπου Γ: 2PL Compliance
>
> "Ελέγξτε αν το schedule τηρεί το 2PL."

**Checklist:**

- [ ] Υπάρχει lock πριν από κάθε read/write;
- [ ] Μετά το πρώτο unlock, δεν υπάρχουν νέα locks;

### 7.2 Συχνές Παγίδες στις Εξετάσεις

❌ **ΛΑΘΟΣ:** "Ακυκλικός precedence graph → ακυκλικός wait-for graph"
✅ **ΣΩΣΤΟ:** Είναι **ανεξάρτητα**. Το ένα μιλάει για correctness, το άλλο για liveness.

❌ **ΛΑΘΟΣ:** "RR είναι σύγκρουση"
✅ **ΣΩΣΤΟ:** Read-Read **ΔΕΝ** είναι σύγκρουση.

❌ **ΛΑΘΟΣ:** "2PL → No deadlocks"
✅ **ΣΩΣΤΟ:** 2PL → Serializability (όχι deadlock-freedom).

❌ **ΛΑΘΟΣ:** "Strict 2PL κρατάει όλα τα locks μέχρι commit"
✅ **ΣΩΣΤΟ:** Strict 2PL κρατάει μόνο τα **X-locks**. Το Rigorous κρατάει όλα.

## 8. Σύνοψη Θεωρημάτων

### Σειριοποιησιμότητα

```
Schedule S είναι Conflict Serializable
⟺
O Precedence Graph του S είναι ακυκλικός
```

### 2PL

```
Όλες οι δοσοληψίες ακολουθούν 2PL
⟹
Το schedule είναι Conflict Serializable
```

(Προσοχή: Δεν ισχύει το αντίστροφο! Υπάρχουν serializable schedules που δεν προκύπτουν από 2PL)

### Deadlock

```
Κύκλος στον Wait-For Graph
⟺
Υπάρχει Deadlock
```

## 9. Πρακτικές Συμβουλές

### 9.1 Πώς να Βρεις Συγκρούσεις Γρήγορα

1. Σημείωσε όλα τα X (αντικείμενα)
2. Για κάθε X, βάλε τις λειτουργίες σε στήλη:

```
X:  R₁  W₂  W₁
    ↓ ↘ ↓
    RW  WW
    1→2 2→1
```

3. Σχεδίασε τις ακμές

### 9.2 Topological Sort για Serial Order

Αν ο γράφος είναι ακυκλικός:

1. Βρες κόμβο χωρίς εισερχόμενες ακμές
2. Βάλτον στην ακολουθία
3. Αφαίρεσέ τον
4. Επανάλαβε
