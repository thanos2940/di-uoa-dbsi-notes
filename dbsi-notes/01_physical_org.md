## 📚 Εισαγωγή: Από τη Λογική στη Φυσική Οργάνωση

Όταν γράφουμε SQL:

```sql
SELECT * FROM Students WHERE age > 20;
```

Το DBMS πρέπει να μετατρέψει αυτό σε **φυσικές λειτουργίες I/O** στον δίσκο. Αυτό το module εξηγεί:

- Πώς αποθηκεύονται τα δεδομένα
- Πώς μετράμε το κόστος
- Πώς λειτουργεί το buffer pool

## 1. Δομή Δίσκου & I/O

### 1.1 Ανατομία Σκληρού Δίσκου (HDD)

**Φυσικά Στοιχεία:**

```
┌──────────────────┐
│   Βραχίονας      │ ← Κινείται (seek)
│      ↓           │
│  ════════════    │ ← Πλατό (περιστρέφεται)
│  ════════════    │
│                  │
└──────────────────┘
```

**Βασικοί Όροι:**

- **Πλατό (Platter):** Ο δίσκος που περιστρέφεται
- **Κύλινδρος (Cylinder):** Όλα τα tracks στην ίδια απόσταση από το κέντρο
- **Τομέας (Sector):** Η μικρότερη μονάδα που διαβάζεται (π.χ. 512 bytes)
- **Track:** Ομόκεντρος κύκλος στην επιφάνεια του πλατό

### 1.2 Χρόνος Πρόσβασης

**Συνολικός χρόνος για ανάγνωση:**

```
Total Time = Seek Time + Rotational Latency + Transfer Time
```

#### Seek Time (Χρόνος Μετακίνησης)

Χρόνος για τον βραχίονα να μετακινηθεί στο σωστό track.

- Τυπικά: **3-10 ms** (milliseconds)
- Εξαρτάται από την απόσταση

#### Rotational Latency (Καθυστέρηση Περιστροφής)

Χρόνος μέχρι να έρθει ο sector κάτω από την κεφαλή.

- Μέση περίπτωση = **μισή περιστροφή**
- 7200 RPM disk: 1 περιστροφή = 60/7200 = 8.33ms → latency ≈ **4ms**

#### Transfer Time (Χρόνος Μεταφοράς)

Χρόνος για μεταφορά bytes.

- Συνήθως **αμελητέος** σε σχέση με seek+latency
- π.χ., 100 MB/s → 4KB μπλοκ = 0.04 ms

**Παράδειγμα:**

```
Seek: 5 ms
Latency: 4 ms
Transfer: 0.05 ms
───────────────
Total: ~9 ms
```

> 💡 **Κρίσιμο συμπέρασμα:** Το **seek και latency κυριαρχούν**. Γι' αυτό ελαχιστοποιούμε τον **αριθμό I/Os**, όχι το μέγεθος.

### 1.3 SSD vs HDD

| Χαρακτηριστικό | HDD | SSD |
|----------------|-----|-----|
| **Μηχανισμός** | Μηχανικά μέρη | Flash memory (NAND) |
| **Seek time** | 3-10 ms | ~0.1 ms (ουσιαστικά 0) |
| **Random I/O** | Αργό | Γρήγορο ✓ |
| **Sequential I/O** | Γρήγορο | Πολύ γρήγορο ✓ |
| **Κόστος/GB** | Χαμηλό | Υψηλό |
| **Αντοχή** | Άπειρα writes | Περιορισμένοι κύκλοι (~10K-100K) |

## 2. Μπλοκ (Blocks) - Η Μονάδα I/O

### 2.1 Τι είναι Μπλοκ

**Μπλοκ (Page, Block):** Η βασική μονάδα μεταφοράς μεταξύ δίσκου και μνήμης.

**Τυπικό μέγεθος:**

- 4 KB (4096 bytes)
- 8 KB (σε μερικά συστήματα)
- 16 KB (για data warehouses)

**Γιατί όχι μικρότερα;**

- Το seek/latency είναι σταθερό → καλύτερα να διαβάζουμε περισσότερα ανά I/O

**Γιατί όχι μεγαλύτερα;**

- Περισσότερη σπατάλη χώρου
- Περισσότερος χρόνος transfer

> 💡 Στις ασκήσεις, θεωρούμε ότι **1 I/O = 1 μπλοκ**.

### 2.2 Ορολογία Κόστους

**Συμβολισμοί (Καθηγητής Ιωαννίδης):**

- $p(R)$: **Αριθμός μπλοκ** (pages) του πίνακα R
- $t(R)$: **Αριθμός εγγραφών** (tuples) του R
- $V(A,R)$: Αριθμός **διαφορετικών τιμών** του πεδίου A

**Παράδειγμα:**

```
Students: 10,000 εγγραφές
Κάθε εγγραφή: 200 bytes
Μέγεθος μπλοκ: 4096 bytes

Εγγραφές ανά μπλοκ = ⌊4096 / 200⌋ = 20
p(Students) = ⌈10,000 / 20⌉ = 500 μπλοκ
```

## 3. Διαχείριση Buffer Pool

### 3.1 Τι είναι το Buffer Pool

**Buffer Pool:** Χώρος στην **κύρια μνήμη (RAM)** για caching μπλοκ του δίσκου.

```
┌───────────────────────────┐
│  RAM (Buffer Pool)        │
│  ┌─────┬─────┬─────┬───┐  │
│  │ Pg1 │ Pg5 │ Pg12│...│  │
│  └─────┴─────┴─────┴───┘  │
└───────────────────────────┘
         ↕ I/O
┌───────────────────────────┐
│  Disk                     │
│  [Page 1][Page 2]...[Pg n]│
└───────────────────────────┘
```

**Πλεονεκτήματα:**

- Αν το μπλοκ είναι ήδη στη μνήμη → **Hit** → 0 I/Os!
- Αλλιώς → **Miss** → 1 I/O για fetch

### 3.2 Metadata ανά Buffer Frame

Κάθε frame (θέση) στο buffer pool έχει:

- **Page ID:** Ποιο μπλοκ περιέχει
- **Pin Count:** Πόσες διεργασίες το χρησιμοποιούν τώρα
- **Dirty Bit:** 1 αν τροποποιήθηκε (χρειάζεται write-back)

### 3.3 Πολιτικές Αντικατάστασης

Όταν το buffer γεμίσει, ποιο μπλοκ εκδιώκουμε;

#### LRU (Least Recently Used)

**Κανόνας:** Εκδίωξε το **λιγότερο πρόσφατα** χρησιμοποιημένο.

**Υλοποίηση:** Linked list ή timestamp.

**Πότε είναι καλό:**

- Sequential scans
- Temporal locality

**Παράδειγμα:**

```
Buffer (M=3): [A, B, C]
Access D → Εκδίωξε το A (oldest)
Buffer: [D, B, C]
```

#### MRU (Most Recently Used)

**Κανόνας:** Εκδίωξε το **πιο πρόσφατα** χρησιμοποιημένο.

**Πότε είναι καλό:**

- **Cyclic access patterns**
- π.χ., Inner table σε nested loop join

> 💡 **Tip του καθηγητή:**
> Στο Nested Loop Join, αν ο inner πίνακας χωράει στη μνήμη:
>
> - LRU θα εκδιώξει τα μπλοκ που θα ξαναχρησιμοποιήσουμε (κακό!)
> - MRU θα κρατήσει τα παλιά μπλοκ (καλό!)

#### Clock (LRU Approximation)

- Χρησιμοποιεί bit "reference" αντί για timestamp
- Πιο αποδοτικό από LRU

## 4. Φυσική Οργάνωση Εγγραφών

### 4.1 Εγγραφές Σταθερού Μήκους

**Παράδειγμα:**

```c
struct Student {
    int id;        // 4 bytes
    char name[50]; // 50 bytes
    float gpa;     // 4 bytes
};
// Total: 58 bytes
```

**Τοποθέτηση στο μπλοκ:**

```
┌────────────────┬────────────────┬────────────────┐
│ Record 1       │ Record 2       │ Record 3       │
│ (58 bytes)     │ (58 bytes)     │ (58 bytes)     │
└────────────────┴────────────────┴────────────────┘
```

**Υπολογισμός διεύθυνσης:**

```
Address(i) = Base + (i-1) × RecordSize
```

**Εγγραφές ανά μπλοκ:**

```
Capacity = ⌊BlockSize / RecordSize⌋
```

### 4.2 Εγγραφές Μεταβλητού Μήκους

**Παράδειγμα:**

```sql
CREATE TABLE Courses (
    code VARCHAR(10),
    description TEXT  -- Μεταβλητό!
);
```

**Τεχνικές:**

#### Slot Directory

```
┌─────────────────────────────────┐
│ Header: [N=3, Free=500]         │
├─────────────────────────────────┤
│ Slot 1: Offset=100, Len=50      │
│ Slot 2: Offset=150, Len=80      │
│ Slot 3: Offset=230, Len=120     │
├─────────────────────────────────┤
│ Free Space                      │
├─────────────────────────────────┤
│ Record 3 (120 bytes)            │
│ Record 2 (80 bytes)             │
│ Record 1 (50 bytes)             │
└─────────────────────────────────┘
```

**Πλεονεκτήματα:**

- Εύκολη διαγραφή (αλλάζουμε μόνο το slot)
- Defragmentation χωρίς να αλλάξουν οι pointers

## 5. Οργάνωση Αρχείου

### 5.1 Heap (Σωρός)

**Ιδέα:** Εγγραφές **χωρίς σειρά**.

**Λειτουργίες:**

- **Insert:** Βάλε στο τέλος → O(1)
- **Search:** Σάρωσε όλο το αρχείο → O(n)
- **Delete:** Βρες και σημείωσε deleted → O(n)

**Πότε χρησιμοποιείται:**

- Logs, temporary tables
- Όταν δεν χρειάζεται ταξινόμηση

### 5.2 Sorted (Ταξινομημένο)

**Ιδέα:** Εγγραφές **ταξινομημένες** με βάση κλειδί.

**Λειτουργίες:**

- **Search:** Binary search → O(log n)
- **Insert:** Βρες θέση + μετακίνηση → O(n) ακριβό!
- **Range query:** Πολύ γρήγορο ✓

**Πότε χρησιμοποιείται:**

- Όταν reads >> writes
- Clustered index

## 6. ISAM (Indexed Sequential Access Method)

### 6.1 Βασική Ιδέα

**ISAM = Ταξινομημένο αρχείο + Στατικό δενδρικό ευρετήριο**

```
        [Index Nodes]
       /      |      \
   [10,20] [30,40] [50,60]  ← Ευρετήριο (ΣΤΑΤΙΚΟ)
   /    |    |    |    |
[Data Pages]           ← Δεδομένα (ταξινομημένα)
```

**Χαρακτηριστικά:**

- Το ευρετήριο κατασκευάζεται **ΜΙΑ ΦΟΡΑ**
- ΔΕΝ αναδιοργανώνεται μετά από updates
- Υποστηρίζει range queries

### 6.2 Δομή

#### Ευρετήριο (Index Levels)

```
Root:        [20, 40, 60]
            /    |    |    \
Level 1:  [5,15] [25,35] [45,55] [65,75]
```

Κάθε κόμβος περιέχει:

- Κλειδιά (separators)
- Δείκτες σε παιδιά

#### Φύλλα (Data Pages)

Ταξινομημένες εγγραφές.

**Σημαντικό:** Τα φύλλα είναι **συνδεδεμένα** (linked) για sequential scan.

### 6.3 Λειτουργίες

#### Search(K)

1. Κάθοδος από root (όπως B+ tree)
2. Φτάσε στο φύλλο
3. (Πιθανή) σάρωση overflow chain

**Κόστος:**

```
Cost = d(I) + overhead από overflow
```

#### Insert(K, R)

1. Βρες το φύλλο
2. Αν χωράει → εισήγαγε ✓
3. Αν ΔΕΝ χωράει → δημιούργησε **Overflow Page**

```
┌──────────┐
│ Page 5   │ → [Overflow 1] → [Overflow 2]
│ [10,20,30]│
└──────────┘
```

**Πρόβλημα:** Οι overflow chains μεγαλώνουν → **αργή αναζήτηση!**

#### Delete(K)

1. Βρες την εγγραφή
2. Σημείωσέ την deleted
3. (Προαιρετικά) διέγραψε αδειασμένα overflow pages

**Πρόβλημα:** Δεν ανακατανέμει χώρο.

### 6.4 Πλεονεκτήματα & Μειονεκτήματα

| ✅ Πλεονεκτήματα | ❌ Μειονεκτήματα |
|-----------------|------------------|
| Απλό σχεδιασμό | Staticό → κακή απόδοση με updates |
| Γρήγορη αναζήτηση (αρχικά) | Overflow chains αυξάνονται |
| Range queries | Δεν αναδιοργανώνεται |

> 💡 **Ιστορική σημασία:** Το ISAM ήταν πρόγονος των **B+ Trees**, που είναι δυναμικά.

## 7. Σύγκριση Οργανώσεων

| Μέθοδος | Search | Insert | Delete | Range | Remarks |
|---------|--------|--------|--------|-------|---------|
| **Heap** | O(n) | O(1) | O(n) | O(n) | Απλό, αργή αναζήτηση |
| **Sorted** | O(log n) | O(n) | O(n) | O(log n + k) | Γρήγορο range, κακό insert |
| **ISAM** | O(log n) | O(1)* | O(1)* | O(log n + k) | *εκτός overflow |
| **B+ Tree** | O(log n) | O(log n) | O(log n) | O(log n + k) | Best overall ✓ |

## 8. Παράδειγμα Υπολογισμών

**Σενάριο:**

- Πίνακας: 1,000,000 εγγραφές
- Κάθε εγγραφή: 100 bytes
- Μέγεθος μπλοκ: 4 KB = 4096 bytes

**Υπολογισμοί:**

```
Εγγραφές ανά μπλοκ = ⌊4096 / 100⌋ = 40

p(Table) = ⌈1,000,000 / 40⌉ = 25,000 μπλοκ

Μέγεθος αρχείου = 25,000 × 4 KB = 100 MB
```

**Κόστος Full Table Scan:**

```
Cost = p(Table) = 25,000 I/Os

Χρόνος (με 10ms ανά I/O) = 25,000 × 10ms = 250 sec = 4+ λεπτά!
```

> 💡 Γι' αυτό χρειαζόμαστε ευρετήρια!
