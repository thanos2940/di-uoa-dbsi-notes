Η Ουσία σε 60 δευτερόλεπτα

ΤΙ ΚΑΝΕΙ
Τα ανώτερα επίπεδα του ΣΔΒΔ βλέπουν μόνο εγγραφές. Από κάτω, οι εγγραφές μπαίνουν σε σελίδες (μπλοκ), οι σελίδες συνθέτουν αρχεία. Χρειάζεται: (α) να ξέρεις ποιες σελίδες έχει ένα αρχείο και πού έχει χώρο, (β) να βρίσκεις μια εγγραφή μέσα στη σελίδα, (γ) να βρίσκεις τα πεδία μέσα στην εγγραφή. Η «διεύθυνση» μιας εγγραφής είναι το RID = (σελίδα, slot).

Διαίσθηση: σκέψου μια πολυκατοικία (αρχείο) με διαμερίσματα (σελίδες) και ενοίκους (εγγραφές). Ο θυρωρός κρατά έναν κατάλογο «ποιο διαμέρισμα έχει άδειο δωμάτιο» (page directory). Μέσα σε κάθε διαμέρισμα, στην πόρτα υπάρχει πίνακας «ένοικος #3 → δωμάτιο στο βάθος αριστερά» (slot directory) — έτσι μπορείς να μετακινείς ενοίκους μέσα στο διαμέρισμα χωρίς να αλλάξει η διεύθυνσή τους (RID).

✅ Slotted page / directory κερδίζει όταν…
  • έχεις εγγραφές μεταβλητού μήκους
  • θες σταθερά RIDs ενώ οι εγγραφές μετακινούνται (compaction)
  • θες γρήγορα σελίδα με αρκετό ελεύθερο χώρο
❌ Συνδεδεμένες λίστες / packed υποφέρουν όταν…
  • ψάχνεις συγκεκριμένο μπλοκ (πρέπει να διαβάσεις όλα τα προηγούμενα)
  • διαγράφεις και θες να συμπιέσεις (μετακινούνται τα RIDs)
  • μια μεγάλη εγγραφή ψάχνει χώρο σε πολλές σελίδες
📝
Για τις εξετάσεις θυμήσου: (1) RID = <page-id, slot-number>. (2) Εγγραφές/μπλοκ (σταθερό μήκος, bitmap) = ⌊(M − κεφαλίδα) / (μ + 1 bit)⌋· διεύθυνση εγγραφής i = A + (i−1)·μ. (3) Slotted: ο κατάλογος slot κρατά <offset, length>, διαγραφή = −1, ο ελεύθερος χώρος είναι ανάμεσα σε εγγραφές και κατάλογο. (4) Page directory με 4B pid + 4B ένδειξη → 4096/8 = 512 entries/σελίδα.

1. Αρχεία & Heap Files

Σε υψηλό επίπεδο το ΣΔΒΔ «βλέπει» μόνο εγγραφές· τα μπλοκ είναι ο περιέκτης τους. Μια σελίδα χωρά περιορισμένες εγγραφές → ένα αρχείο = συλλογή μπλοκ (με κενά «free» ανάμεσα).

Heap file
  • Ο πιο απλός τρόπος οργάνωσης: καμία διάταξη.
  • Καθώς μεγαλώνει/μικραίνει, δεσμεύονται/αποδεσμεύονται μπλοκ.
  • Για πράξεις σε επίπεδο εγγραφής χρειάζεται: να ξέρουμε ποια μπλοκ έχει το αρχείο, να βρίσκουμε εγγραφές μέσα σε κάθε μπλοκ, και πεδία μέσα σε κάθε εγγραφή.

Heap file με συνδεδεμένα μπλοκ

Το header block δεσμεύεται με το CreateFile(name). Από αυτό ξεκινούν δύο διπλά συνδεδεμένες λίστες: γεμάτες σελίδες και σελίδες με ελεύθερο χώρο (αρχικά άδειες). Νέες εγγραφές → το ΣΔΒΔ παίρνει μπλοκ από τον δίσκο.

2. API Αρχείου & η φύση του RID

Κάθε εγγραφή heap file έχει Record ID (RID) = διεύθυνση/δείκτης της εγγραφής· η δομή του heap file αντιστοιχίζει RID → σελίδα.

function InsertRecord(fd, rec): p = σελίδα από τη λίστα free-space με χώρο ≥ |rec| if p == NULL: ο Disk Manager δεσμεύει νέα σελίδα p γράψε rec στη p // |p| ≫ |rec| return μοναδικό RID
RID → (p, d): σύνθετο αναγνωριστικό = σελίδα p + μετατόπιση d (θέση, αριθμός slot) της εγγραφής μέσα στο μπλοκ. Στη σελίδα: RID = <page-id, slot-number>. Έχουν χρησιμοποιηθεί και μοναδικά surrogate IDs (SRID) αλλά με μεγάλο κόστος διαχείρισης.

3. Heap File με Κατάλογο Σελίδων (Page Directory)

Βελτίωση: ένα σύνολο header/directory pages λειτουργεί ως κατάλογος των data blocks.

  • Οι directory pages κρατούν διευθύνσεις των data blocks.
  • Κάθε entry μπορεί να έχει και πόσο «άδειο» είναι το μπλοκ → space map.
  • Πολλές directory pages συνδεδεμένες αν χρειαστεί· είναι ελάχιστες σε σχέση με τις σελίδες δεδομένων· ο κατάλογος μεγαλώνει/μικραίνει.
  • Ελεύθερος χώρος από διαγραφές → διαχειρίζεται στον κατάλογο: τουλάχιστον 1 bit ανά entry (γεμάτη/όχι)· πιο ακριβής πληροφορία = trade-off χώρου vs ακρίβειας.
  • Κόστος μνήμης σε αντάλλαγμα για γρηγορότερη πρόσβαση σε μπλοκ με συγκεκριμένο pid.

5. Εγγραφές Σταθερού Μήκους μέσα σε Μπλοκ

Δύο μεγάλες επιλογές (πίνακας διάλεξης): σταθερό πακετάρισμα (εγγραφές η μία μετά την άλλη, ακόμα και πάνω από όρια μπλοκ) ή εγγραφές ολόκληρες σε 1 μπλοκ (με κεφαλίδα και ευρετήριο εγγραφών).

Α. Σταθερό πακετάρισμα (πίνακας διάλεξης)

A→εγγραφή 1εγγραφή 2εγγρ. 3|όριο μπλοκ|…3 (συνέχεια)εγγρ. 4|όριο|…
Διεύθυνση εγγραφής εi
  • Σταθερό μήκος μ: A + (i − 1)·μ
  • Μεταβλητό μήκος μk: A + Σk=1i−1 μk
+
  • γρήγορος υπολογισμός θέσης εγγραφής
  • πυκνότητα χώρου, καθόλου σπατάλη
−
  • σχεδόν αδύνατη η διαγραφή εγγραφής (π.χ. χρειάζεται έξτρα bit 0/1)
  • εγγραφές «διασχίζουν» μπλοκ: μια λογική προσπέλαση γίνεται >1 φυσικές
  • σχεδόν αδύνατη η αλλαγή σχήματος
  • πολύ μεγάλη προδέσμευση χώρου για αύξηση αρχείου

Β. Εγγραφές ολόκληρες σε 1 μπλοκ

Packed (διαφάνεια 34)
hdr: nslot1slot2slot3… slot nκενά slots

Η κεφαλίδα έχει το πλήθος n. Οι εγγραφές ακολουθούν συνεχόμενα, τα κενά slots στο τέλος. Διαγραφή → συμπίεση (μετακίνηση της τελευταίας στην «τρύπα»).

Unpacked + bitmap (διαφάνεια 35)
slot1κενόslot3κενόslot5bitmap 1 0 1 0 1n

Η κεφαλίδα έχει bitmap: 1 = slot με εγγραφή, 0 = κενό. Γεμάτα και κενά slots ανακατεμένα. Πίνακας διάλεξης: «bits ύπαρξης» στο τέλος του μπλοκ.

Packed vs Unpacked+Bitmap — take-away
Στο packed ο κενός χώρος πάντα μένει «τρύπα» μέχρι να γίνει compaction. Αν τα RIDs είναι σταθερά και τα χρησιμοποιούν ανώτερα modules, η μετακίνηση εγγραφών μέσα στη σελίδα είναι πρόβλημα (αλλάζει το slot!). Το bitmap το λύνει: η διαγραφή απλώς μηδενίζει ένα bit.
Τύπος πίνακα διάλεξης: πόσες εγγραφές χωρά ένα μπλοκ;

εγγραφές/μπλοκ = ⌊ (M − κεφαλίδα) / (μ + «1 bit») ⌋

M = μήκος μπλοκ, μ = σταθερό μήκος εγγραφής· το «1» είναι το bit ύπαρξης κάθε εγγραφής. Παράδειγμα: M = 4096 B, κεφαλίδα 32 B, μ = 100 B → (4064·8 bits)/(801 bits) = 32.512/801 = 40,6 → 40 εγγραφές. Η κεφαλίδα περιέχει: περιγραφή, δείκτη στο επόμενο μπλοκ, δείκτες υπερχείλισης…

6. Slotted Page — Εγγραφές Μεταβλητού Μήκους

Δουλεύει για μεταβλητού και σταθερού μήκους εγγραφές. Πίνακας διάλεξης: «ευρετήριο + κεφαλίδα»· «όπως για τα πεδία μεταβλητού μήκους στις εγγραφές, έτσι και για τις εγγραφές μεταβλητού μήκους σε μπλοκ».

headerεγγρ. 1 (60B)εγγρ. 2 (100B)διαγρ.εγγρ. 4⟵ ελεύθερος χώρος ⟶4:<260,50>3:<−1>2:<60,100>1:<0,60>N=4
Οι εγγραφές μεγαλώνουν από αριστερά, ο κατάλογος slots από δεξιά· ο ελεύθερος χώρος είναι στη μέση.
  • Κάθε σελίδα έχει κατάλογο i = 1..N slots· το slot i κρατά <record-offset, record-length>.
  • Το RID αποσυνδέεται από τη φυσική θέση: οι εγγραφές μπορούν να μετακινηθούν μέσα στη σελίδα (compaction) αφού το entry του καταλόγου δεν αλλάζει όσο η εγγραφή είναι ενεργή.
  • Ελεύθερος χώρος = η περιοχή ανάμεσα στις εγγραφές και τον κατάλογο slots· αν μια νέα εγγραφή πάρει χώρο από εκεί, ο κατάλογος μπορεί να αποκτήσει νέα slots.
  • Διαγραφή: το entry γίνεται −1· τα άδεια slots ξαναχρησιμοποιούνται σε εισαγωγή αν ταιριάζει το μέγεθος.

7. Πεδία μέσα στην Εγγραφή

Ο κατάλογος (catalog) του ΣΔΒΔ ξέρει πόσα πεδία, τι τύπου και με ποια σειρά. Ορισμοί (πίνακας): Αρχείο = σύνολο εγγραφών · Εγγραφή = διατεταγμένο ή ανοργάνωτο σύνολο πεδίων · Πεδίο = ατομικό στοιχείο με συγκεκριμένη τιμή · όλες οι εγγραφές ενός αρχείου έχουν τα ίδια πεδία.

Σταθερό μήκος πεδίων
base→F1 (L1)F2 (L2)F3 (L3)F4 (L4)

Διεύθυνση του F3 = base + L1 + L2. Γενικά (πίνακας): διεύθυνση Πi = δ + Σk=1i−1 μk. Εναλλακτικά (πίνακας διάλεξης): ευρετήριο δεικτών στην αρχή της εγγραφής → τα πεδία μπορούν να είναι σε τυχαία σειρά· διεύθυνση Πi = δ + δi.

Μεταβλητό μήκος πεδίων

(α) Διαχωριστικά — ειδικό σύμβολο στο τέλος κάθε πεδίου:

F1#F2#F3#F4#

(β) Μήκος στην αρχή κάθε πεδίου (πίνακας διάλεξης):

l1F1l2F2l3F3

(γ) Πίνακας ακέραιων offsets στην αρχή της εγγραφής:

o1o2o3o4F1F2F3F4
⚠️ NULL & προβλήματα των offsets
Πώς αναπαριστάς NULL; Ο πίνακας offsets επαυξάνεται με το μήκος κάθε πεδίου → NULL = μήκος 0. Προβλήματα: τι γίνεται αν ένα πεδίο τροποποιηθεί και χρειάζεται περισσότερο χώρο; Χειρότερα, η αλλαγή μπορεί να «ξεχειλίσει» σε νέο μπλοκ — εγγραφές που απλώνονται σε >1 μπλοκ!

8. Γραμμοειδής vs Στηλοειδής Αποθήκευση (ORC, Parquet)

Row-wise (κυρίαρχο)

Κάθε πλειάδα ολόκληρη μέσα σε ένα μπλοκ, συνήθως slotted. PostgreSQL & DB2 υποθέτουν «λογικό» μήκος εγγραφής που χωρά σε ένα μπλοκ.

a1 b1 c1a2 b2 c2a3 b3 c3
Column-wise

Κάθε μπλοκ περιέχει ένα μόνο πεδίο. Trade-off: φθηνή ανάγνωση λίγων στηλών / συμπίεση, ακριβή ανασύνθεση ολόκληρης πλειάδας.

a1 a2 a3 a4 a5b1 … b5c1 … c5

Data-science αλγόριθμοι και αναλυτικά ερωτήματα σε δισεκατομμύρια γραμμές θέλουν οργανώσεις για γρήγορη, παράλληλη/κατανεμημένη επεξεργασία: Apache Parquet (Pandas, Polars, PyArrow, DuckDB, Spark) και Apache ORC (Java περιβάλλοντα).

ORC (Optimized Row Columnar)
  • Self-describing, type-aware.
  • Η ανάγνωση ξεκινά από τα τελευταία bytes: Postscript (συμπίεση, μήκος footer) & File Footer (σχήμα, global στατιστικά).
  • Stripes των 64–256 MB, το καθένα με Stripe Footer και Row Group Indexes κάθε 10.000 γραμμές: min, max, sum, null counts → παράλειψη μπλοκ που δεν χρειάζονται.
Parquet (υβριδικό)
  • Row-groups (128 MB–1 GB) = οριζόντιες φέτες· μέσα σε κάθε row-group, column chunks συνεχόμενα στον δίσκο· chunks → pages (~1 MB, και dictionary pages).
  • Header: 4 bytes PAR1. Footer: schema, #tuples, key-values, row-group metadata (offsets, min/max, null count, μεγέθη, encoding), footer length 4B, trailing PAR1.
  • Projection pushdown: παρακάμπτει στήλες που δεν ζητήθηκαν. Predicate pushdown: με min/max, π.χ. id > 1250 → πηδά ολόκληρα row-groups. Logical type mapping (TIMESTAMP, DECIMAL, VARCHAR).
Parquet: name/id/when σε 3 row-groups
RG-0Abc Bcd Cde1001 1003 111301-01-26 03-01-26 15-02-25
RG-1Def Efg Fgh1119 1120 200112-12-24 01-01-23 12-09-25
RG-2Ghi Hij2004 200910-09-25 09-09-26
Ερώτημα id > 1250: min/max του RG-0 = 1001..1113, RG-1 = 1119..2001, RG-2 = 2004..2009 → το RG-0 παραλείπεται ολόκληρο.
