Αλγόριθμοι Ζεύξης (Join Algorithms)

Εισαγωγή

Η λειτουργία JOIN είναι η πιο κοστοβόρα πράξη στη βάση δεδομένων. Το 60-70% του χρόνου στα πολύπλοκα queries ξοδεύεται στα joins.

Ο Optimizer πρέπει να επιλέξει τον κατάλληλο αλγόριθμο ανάλογα με:

  • Το μέγεθος των πινάκων (\(p(R), p(S)\))
  • Τη διαθέσιμη μνήμη (\(M\) buffers)
  • Την ύπαρξη ευρετηρίων

Τύποι Ζεύξεων

Οι ασκήσεις εστιάζουν κυρίως στο Equi-Join (Ισότητα).

-- Equi-Join (Ισότητα)
SELECT * FROM R, S WHERE R.A = S.B

-- Natural Join (Ισότητα στα κοινά πεδία)
SELECT * FROM R NATURAL JOIN S

1. Nested Loop Join (NLJ)

1.1 Simple Nested Loop (Tuple-based)

Ιδέα: "Για κάθε εγγραφή του R, σάρωσε όλο τον S".

Κόστος: \(p(R) + t(R) \times p(S)\)

Απαράδεκτα αργό! Δεν χρησιμοποιείται στην πράξη.

Tuple-based Nested Loop Visualizer

Για κάθε εγγραφή του R (outer), σαρώνουμε ολόκληρο τον S (inner).

1.2 Block Nested Loop (Page-oriented) SOS

Ιδέα: Φέρνουμε block (σελίδα) του R στη μνήμη και τη συγκρίνουμε με κάθε block του S. Αυτό μειώνει δραματικά τις σαρώσεις του εσωτερικού πίνακα.

Visual Flow:
For each block Br in R:
  For each block Bs in S:
    For each tuple tr in Br:
      For each tuple ts in Bs:
        if match(tr, ts): output(tr, ts)

Με Buffer \(M\) σελίδων

Βέλτιστη στρατηγική:

  • \(M-2\) σελίδες για τον Outer (chunks).
  • 1 σελίδα για τον Inner (S).
  • 1 σελίδα για Output.
Κόστος: $$p(R) + \left\lceil \frac{p(R)}{M-2} \right\rceil \times p(S)$$

Όπου \(\lceil p(R)/(M-2) \rceil\) είναι το πλήθος των chunks.

Στρατηγική: Ποιος πίνακας Outer;

Πάντα βάζουμε Outer τον πίνακα με τις λιγότερες σελίδες \(p(R)\).
Έτσι ελαχιστοποιούμε τον όρο \(\lceil \frac{p(Outer)}{M-2} \rceil \times p(Inner)\).

Solved Example: Block NL

Δεδομένα: \(p(R)=100\), \(p(S)=50\), \(M=12\).

Λύση:

  1. Επιλέγουμε Outer = S (50 < 100).
  2. Chunks του S = \(\lceil 50 / (12-2) \rceil = \lceil 50/10 \rceil = 5\).
  3. Cost = \(50 + 5 \times 100 = 550\) I/Os.

(Αν βάζαμε Outer το R: \(100 + 10 \times 50 = 600\) I/Os. Χειρότερο!)

1.3 Index Nested Loop Join (INLJ)

Προϋπόθεση: Ύπαρξη ευρετηρίου (π.χ. B+ Tree) στο πεδίο σύνδεσης του εσωτερικού (inner) πίνακα.

Ιδέα: Αντί να σαρώνουμε όλο τον S, για κάθε εγγραφή του R κάνουμε index lookup στον S.

Κόστος: $$p(R) + t(R) \times Cost_{Lookup}(S)$$

Το \(Cost_{Lookup}\) για ένα B+ Tree είναι συνήθως 2-4 I/Os.

ΠΡΟΣΟΧΗ: Αν το ευρετήριο είναι Clustered, το κόστος είναι πολύ χαμηλό. Αν είναι Unclustered και έχουμε πολλά matches ανά κλειδί, το κόστος μπορεί να εκτοξευθεί!

2. Sort-Merge Join

2.1 Βασική Ιδέα

Αν οι πίνακες είναι ταξινομημένοι, τους σαρώνουμε παράλληλα (merge) με κόστος \(p(R) + p(S)\).

Αν ΔΕΝ είναι, πρέπει πρώτα να τους ταξινομήσουμε (External Merge Sort).

Συνολικό Κόστος: $$Cost = Cost_{sort}(R) + Cost_{sort}(S) + p(R) + p(S)$$

Κόστος External Sort

Το κόστος για να ταξινομήσουμε έναν πίνακα \(R\) με \(M\) buffers είναι:

$$Cost_{sort}(R) = 2 \cdot p(R) \cdot Passes$$ $$Passes = 1 + \lceil \log_{M-1}(\lceil p(R)/M \rceil) \rceil$$
  • Το "1" είναι το initial pass (δημιουργία runs).
  • Ο λογάριθμος είναι τα merge passes.
  • Το επί 2 είναι γιατί κάθε pass έχει Read + Write.

Solved Example: Sort-Merge

Δεδομένα: \(p(R)=100\), \(p(S)=50\), \(M=10\).

1. Sort R (100 pages):

  • Initial Runs = \(\lceil 100/10 \rceil = 10\).
  • Passes = \(1 + \lceil \log_9(10) \rceil = 1 + \lceil 1.048 \rceil = 1 + 2 = 3\).
  • Cost(R) = \(2 \times 100 \times 3 = 600\).

2. Sort S (50 pages):

  • Initial Runs = \(\lceil 50/10 \rceil = 5\).
  • Passes = \(1 + \lceil \log_9(5) \rceil = 1 + 1 = 2\).
  • Cost(S) = \(2 \times 50 \times 2 = 200\).

3. Merge Cost: \(100 + 50 = 150\).

Total: \(600 + 200 + 150 = 950\) I/Os.

3. Hash Join

3.1 Βασική Ιδέα

Χρησιμοποιούμε hashing για να σπάσουμε το πρόβλημα σε μικρά buckets.

  1. Partitioning: Σπάμε R και S σε \(k\) partitions.
  2. Build & Probe: Για κάθε partition, κάνουμε in-memory join.
Κόστος: $$Cost = 3 \times (p(R) + p(S))$$

Εύκολο στην απομνημόνευση: 3 φορές το άθροισμα!

Προϋπόθεση Μνήμης (Critical!)

Για να δουλέψει, το μικρότερο partition πρέπει να χωράει στη μνήμη.

$$min(p(R), p(S)) \le M \times (M-2)$$
Πότε το επιλέγουμε;
Όταν έχουμε Equality Join (R.A = S.B) και αρκετή μνήμη. Συνήθως είναι ο νικητής!

4. Συνοπτική Σύγκριση & Checklist

Αλγόριθμος Κόστος (I/Os) Best Use Case
Block NL \(p(O) + \lceil \frac{p(O)}{M-2} \rceil \times p(I)\) Μικροί πίνακες, λίγη μνήμη.
Sort-Merge Very high (sort) + Merge Ήδη sorted data.
Hash Join \(3(p(R) + p(S))\) Equality joins, μεγάλοι πίνακες.

Exam Checklist

  • Βρήκα ποιος πίνακας είναι μικρότερος (Outer);
  • Χρησιμοποίησα \(M-2\) στον παρονομαστή του Block NL;
  • Υπολόγισα σωστά τα passes του Sort;
  • Έλεγξα αν χωράει το Hash partition στη μνήμη;

Συχνή Παγίδα

Μην μπερδεύετε το \(p(R)\) (σελίδες) με το \(t(R)\) (εγγραφές)!

Το I/O cost μετριέται πάντα σε σελίδες.
